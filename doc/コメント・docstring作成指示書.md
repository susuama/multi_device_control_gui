# コメント・docstring作成指示書

対象コードのコメントとdocstringを、以下の基準で作成・修正してください。

## 1. 基本方針

コメントは、読者がその場所のコードだけでは判断できない情報を補ってください。
別の関数を調べなくても処理を追えるようにしつつ、コードを読めば十分理解できる説明は省いてください。

説明の量や行数をそろえる必要はありません。単純な処理は短くし、関数間の責任分担、非同期処理の完了条件、失敗時の扱いには必要な説明を残してください。

## 2. 場所ごとの読者の前提

| 場所 | 前提としてよい知識 | 説明する内容 |
|---|---|---|
| モジュール・クラスのdocstring | Pythonの基本知識。ロックや非同期処理の仕組みも前提にしてよい。 | 担当する役割、登場する要素の関係、データの流れ、利用方法と重要な制約。 |
| 関数のdocstring | クラスの役割は理解している。関数内部の実装は知らない。 | その関数が何をするか、呼び出す条件、入力と結果、必要な副作用・例外・待機条件。 |
| 関数内部のコメント | その関数のコードを読んでいる。関連する別の関数の実装までは知らない。 | 呼び出し先の作用、値や通知の意味、処理順序の理由など、その場のコードから分からない情報。 |

ロック、スレッド、Event、Queue、例外処理などの一般的な使い方を解説する必要はありません。そのコードで何を同期し、何を待ち、どの処理へ影響するかを説明してください。

## 3. コメントを残す判断基準

次のいずれかに当てはまる説明を優先してください。

- 別の関数を呼んだ結果、何が変わるかが名前だけでは分からない。
- 完了通知やフラグの意味を誤解しやすい。
- ロックの対象や取得順序に、その処理固有の理由がある。
- データのコピー、処理順序、受付停止の位置に意味がある。
- 失敗した後に、何を終了し、何を保持し、何を再試行できるかが分かりにくい。
- 外部機器やファイル形式など、コードから読み取れない制約がある。

例えば、「命令処理の完了」と「ファイルの保存終了」が異なる場合は、その違いを明記してください。「停止を試み終えた」というフラグを、「停止に成功した」と読める説明にしないでください。

一方、以下の説明は原則として省いてください。

- 代入、条件分岐、ループ、returnなどを日本語に置き換えただけの説明。
- 関数名・変数名・型から分かる内容の繰り返し。
- Python標準機能の一般的な動作説明。
- 近くのdocstringやコメントと、同じ読者に同じ内容を伝える重複。
- 現在の実装に対応しない将来構想や変更履歴。

## 4. docstringの書き分け

### モジュールとクラス

モジュールでは、登場する要素とデータの流れを中心に説明してください。
クラスでは、担当する責任、使い方、利用上の制約、終了時の扱いを中心に説明してください。
両方に同じ仕組みの説明をそのまま繰り返さないでください。

データクラスでは、データ全体の用途と、複数のフィールドの関係を説明してください。
フィールドごとのコメントは、単位、基準時刻、値の意味など、名前や型で不足する情報に絞ってください。

### 関数

冒頭の一文で役割を説明し、利用者が知る必要のある条件を補ってください。
内部の実行手順を一行ずつ説明する必要はありません。

Pythonでは、必要に応じて次の形式を使用してください。

```python
def function(argument: str) -> bool:
    """関数の役割を簡潔に説明する。

    Args:
        argument (str): 利用者が知る必要のある意味や制約。

    Returns:
        bool: 呼び出し元が結果をどう解釈するか。

    Raises:
        RuntimeError: 利用者が知る必要のある失敗条件。
    """
```

引数や戻り値がない場合は、対応するセクションを省いてください。
単純な関数では一文だけでも構いません。形式を満たすためだけのセクションや、想定し得る例外の網羅的な列挙は不要です。

## 5. 関数内部のコメントの書き方

説明対象の直前、または短いフィールド説明なら行末に置いてください。
コメントの説明範囲は、直後の呼び出しやコードブロックに合わせてください。

別の関数を呼ぶ場合は、その場の理解に必要な作用を短く補ってください。
呼び出し先の内部手順まで転載する必要はありません。
作用が関数名と周囲のコードから十分分かる場合は、コメントを付けないでください。

同じ事実でも、関数の利用者と呼び出し箇所の読者にそれぞれ必要なら、docstringとコメントの両方に書いて構いません。
例えば、docstringに「終了を要求し、完了は待たない」と書き、呼び出し箇所にも「保存終了は別途待つ」と補うことには意味があります。

### 例：コードだけで分かる説明は省く

```python
# このコメントは不要。条件とreturnで分かる。
if not self._is_recording:
    return
```

実際のコードには、上の説明用コメントも残さず、if文だけを書いてください。

### 例：待機を区切る理由を書く

```python
# Processorの停止を検出できるよう、完了待ちを最大0.5秒ごとに区切る。
if command.done.wait(timeout=0.5):
    break
```

ここでは、Event.waitの一般的な動作や戻り値の説明を追加しません。

### 例：呼び出し先の作用を補う

```python
# 保存受付を止め、別スレッドでの最終保存を要求する。ここでは完了を待たない。
self._request_recording_stop()
```

### 例：ロック外で待つ理由を補う

```python
# 終了するProcessorも最後に_state_lockを取得するため、ロック外で終了を待つ。
thread.join(timeout=self.STOP_TIMEOUT)
```

これらは書き方の例です。実際のコードでは、呼び出し先やスレッドの動作を確認し、その実装に合う説明だけを使ってください。

## 6. 作業と確認

1. 対象コードと、説明に必要な呼び出し先を確認してください。既存コメントも実装と照合してください。
2. 指定されたファイルだけを編集してください。コピー側の修正を依頼された場合は、元ファイルを保持してください。
3. 各説明を「コードから分かる内容」「その場で必要な補足」「上位のdocstringへ置く内容」に分け、重複と自明な説明を削ってください。
4. 呼び出し元、実行するスレッド、要求と完了、成功と試行済み、受付停止とリソース解放を混同していないか確認してください。
5. コメントを読むために別の関数を開く必要がないか、逆にコードを読む妨げになる説明がないか確認してください。
6. コメント・docstringだけの修正では、処理のコードを変更しないでください。構文チェックと、docstringを除いた構文木やコメント・docstringを除いたトークン列の比較などで確認してください。
7. 結果には、修正したファイル、削った説明と残した説明、実施した確認を簡潔に記載してください。未確認の動作を確認済みとしないでください。
