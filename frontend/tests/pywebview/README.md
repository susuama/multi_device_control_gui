# pywebviewでの中核検証

製品の共有ストア・操作判定・runtime・WebSocketクライアントを、実際のWindows WebView2で検証する。バックエンドの不足APIは、確定済みの `frontend/docs/core-api-contract.md` に従うモックで再現する。製品バックエンドや機器ドライバーは読み込まず、CSV・動画ファイルも作成しない。

## 実行

リポジトリのルートで、依存導入済みの仮想環境と `frontend/node_modules` を使う。

```powershell
.\.venv\Scripts\python.exe frontend/tests/pywebview/run.py --output "$env:TEMP/core-verification.json"
```

10分間の継続受信も含める場合：

```powershell
.\.venv\Scripts\python.exe frontend/tests/pywebview/run.py --soak-seconds 600 --output "$env:TEMP/core-verification.json"
```

ランチャーは検証画面の型チェックとビルドを行い、空いているローカルポートで画面とモックAPIを配信する。製品のVite設定や8000番ポートは使わない。ビルドとWebView2プロファイルは結果ファイルと同じ親ディレクトリ内の一時フォルダに置く。通常のアプリ設定は変更しない。

初回プロセスで操作と設定保存を確認し、同じURL・プロファイルで別プロセスを起動して復元を確認する。画面は一時的に表示・最小化され、継続受信中は非表示になる。終了時にGUI・サーバーを閉じ、一時フォルダを回収する。WebView2が一時ファイルを保持している場合は、一部のファイルが残ることがある。

結果JSONの `ok` と両方の `runs[].ok` がtrueなら成功。失敗時は `error` を確認する。GUIプロセスの出力は、結果ファイル名の拡張子を `.first.log`、`.restore.log` に置き換えたファイルに残す。継続受信中は `.first.log` に30秒ごとの進捗を出す。実行環境には、ローカルHTTP・WebSocket通信とネイティブGUIを許可する必要がある。

## 実バックエンドとの結合確認

模擬APIの検証とは別に、製品のFastAPI・MeasurementManager・DataRecorderとダミードライバーを使い、
EdgeのヘッドレスブラウザーとWebView2で同じ操作を確認する。

```powershell
.\.venv\Scripts\python.exe frontend/tests/pywebview/run_real.py --output "$env:TEMP/real-backend-verification"
```

機器一覧からカメラ1台と数値機器2台を探索し、共有ストア・操作判定・runtime・WebSocketクライアントを通して操作する。
通常画面へ検証用ビューを登録せず、既存のAPI診断画面と模擬API検証を維持する。
ブラウザーはヘッドレス、WebView2は検証専用の非表示ウィンドウで実行する。実機は使用しない。

- 2パネルのDOM表示一致、数値と最新画像の共有、32×24 JPEGの実デコード。
- 実CSVとROI動画の保存、FPS変更の拒否、ゲイン変更、開始時設定の保持。
- 個別取得の停止・再開始、記録終了待ち中の状態GET、停止要求の重複防止。
- Queueへ301件を投入して監視停止を起こし、全取得停止と記録継続を確認する。
- カメラ保存へ失敗を注入し、数値受信・保存の継続と対象別結果を確認する。
- HTTPの503応答とWebSocket切断で通信異常を再現し、最後の値の保持と変更操作を再送しない復旧を確認する。
- 製品lifespanの終了・再生成による起動ID更新、履歴の切り替え、明示的な再開。
- パネル解除と取得の独立、dispose後のWebSocket・定期取得・再接続待機の回収。

障害注入と計測の `/_test/*` 経路は、このランチャーが作る検証サーバーにだけ存在する。
通常のAPI・ドライバーのソースや設定は変更しない。ネットワーク機器の物理切断を再現する検証ではない。
保存先、ビルド、ブラウザープロファイル、WebView2プロファイルはすべて出力ディレクトリ内へ置き、検証結果と保存ファイルを残す。
`result.json` の `ok` と、browser・webview両方の `runs[].ok` がtrueなら成功。

## 模擬APIで確認する内容

- WebView2の描画エンジン・実際のRuntimeバージョン・User-Agent、pywebviewのバージョン。
- 2パネルへの同じ確定状態の表示と、画面操作からの共通ストア呼び出し。
- 同じ機器への重複操作が拒否され、HTTPを二重送信しないこと。
- 数値履歴とJPEGの共有、実際のJPEGデコード。
- FPSの設定ロックとゲイン更新、記録開始時設定の保持。
- 記録終了待機中の状態GET、停止要求の重複防止、取得の継続。
- HTTP成功でも不正な変更応答なら結果不明とし、変更要求を再送せず状態を再確認すること。
- 測定IDの切替と、古い期間の数値・画像の遅延配信を採用しないこと。
- パネルの解除・再表示と最小化・復帰で、取得や受信管理を終了しないこと。
- 通信断で最後の値を保持し、復旧しても取得・記録の開始要求を自動送信しないこと。
- 配色・日本語を含む標準保存先の保存と、アプリ再起動後の復元。
- 共通層のdispose後にWebSocketが0本となり、APIの定期取得も止まること。

変更操作の前は、状態確認と送信を同じJavaScriptのターンで行う。周期GETの途中で未確認として拒否された操作を、検証側が変更要求ごと再試行する方式にはしない。

## 継続受信の条件と限界

カメラ1台（640×480、20 FPS相当の配信間隔）、数値機器2台（各10 Hz相当の配信間隔）を模擬する。JPEGは固定画像で、通信やスケジューリングにより実際の到達頻度は変わる。要求回数と機器別の送信件数を記録する。

30秒ごとに数値の保持件数（各1,000件以内）、画像の保持数（1枚）、WebSocket数（2本）、runtimeの状態を検査する。フレーム番号・通知回数・機器別の受信時刻が進み続けることも確認する。フレーム番号、通知回数、API回数、メモリの参考値を記録する。`heap_bytes` はWebView2が公開する `performance.memory.usedJSHeapSize` で、未対応ならnull。粗い値であり、WebView2プロセス全体や画像のネイティブメモリを測定した値ではない。

この試験は固定した模擬条件で中核の受信・共有処理を確認する。実機の最大性能、製品用グラフ・画像ビュー、バックエンドの保存終了処理、複数ネイティブウィンドウ間の共有は検証しない。ブラウザー履歴からの復元も今回の対象外。

## 2026-11-02の検証結果

Windows、pywebview 6.2.1、WebView2 Runtime 156.0.4314.58で確認した。

- `npm test`：63件成功。`npm run build`、`npm run lint`、検証画面の型チェックも成功。
- 実WebView2での操作、共有、通信復旧、共通層の終了、別プロセスでの設定復元に成功。
- 600秒の継続受信で20回計測。数値の保持は各1,000件、画像は1枚、接続は2本を維持し、フレーム番号と通知回数は各計測で増加した。
- 30秒ごとのJSヒープ参考値は3,534,640〜6,100,839バイトで増減した。プロセス全体のメモリや、長時間のメモリリークがないことを保証する結果ではない。
- dispose後の接続は0本となり、API回数の増加も止まった。
- 計測項目を追加したランチャーでも30秒の受信と設定復元を再確認し、機器別の受信時刻の進行検査が通った。

## 構成

| ファイル | 役割 |
|---|---|
| `fixture.html`、`fixture.tsx` | 検証専用の2パネル画面。製品用ビューには登録しない。 |
| `vite.config.ts`、`tsconfig.json` | 検証画面だけを型チェック・ビルドする。製品distへ混ぜない。 |
| `mock_api.py` | HTTP・WebSocket、試験用の状態切替と計測。 |
| `run.py` | ビルド、モック起動、WebView2の操作、再起動、結果の保存。 |

検証に使う `_test` ルートと `window.coreTest` は検証用アプリ・画面だけに存在し、製品のAPIや画面には追加しない。
