# デバイス設定画面の構成と送信制御

採用日：2026-11-08。対象は既存の `camera` / `power_meter`。外部プラグイン読込や万能なフォーム生成は導入しない。

## 配置と責任

| 場所（frontend/src/以下） | 担当 |
|---|---|
| `devices/camera/settings.ts` | 設定型、編集値の型、応答検証、露光時間ms/秒変換、差分の結合、適用方法 |
| `devices/camera/CameraSettingsForm.tsx` | カメラ固有の項目、単位、現在の画像・ROI表示 |
| `devices/powerMeter/settings.ts` | 設定型、編集値の型、応答検証、入力検証、差分の結合、適用方法 |
| `devices/powerMeter/PowerMeterSettingsForm.tsx` | パワーメーター固有の項目と表示 |
| `devices/settingsContracts.ts` | Reactに依存しない固定登録と設定型の集約。API応答と記録開始時設定の検証もこの登録を使う |
| `devices/settingsForms.tsx` | 同じキーのReactフォーム登録。設定処理とフォームの組合せ・登録漏れを型で検査 |
| `devices/settingsValues.ts`、`SettingsField.tsx`、`settingsFormTypes.ts` | 必要な共通の値検証・比較、入力部品、フォームの受け渡し型 |
| `views/DeviceSettingsView.tsx` | 対象選択、機器情報、入力保持、フォーム選択、適用・破棄・再取得、状態表示 |
| `state/settingsUpdates.ts` | 同一機器への送信の直列化、最新値への集約、待機・取消し・失敗停止 |
| `state/backendStore.ts`、`operationPolicy.ts` | HTTPの確定値、応答検証、競合操作と記録中のロック |

フォームからHTTPや共有ストアへアクセスしない。入力変更と確定を共通画面に通知する。`DeviceInfo.type` を選択キーに使い、未登録種類は未対応として拒否する。他種類の検証器・フォームへ流さない。未対応の接続機器を全体取得で検出した場合は従来の同期エラー経路を使い、確定済みの他機器の値を保持する。

## 入力と適用

適用方法は編集値のキーに対応する `modes` で定義する。入力部品は数値・チェック・既存の選択欄を維持し、スライダーの範囲を推測しない。

| 機器 | 即時反映 | ボタン適用 |
|---|---|---|
| カメラ | exposure（表示ms、API秒）、gain | gain_boost、fps |
| パワーメーター | なし | wavelength、range、auto_range、bandwidth、averaging |

この個別割当はユーザーによる各項目の指定ではなく、採用した仕組みを動かすための初期実装案である。

表示中の操作値はパネル・機器・バックエンド起動IDごとの下書きとして保持する。周期取得、他パネルの適用、ビュー切替で消さない。変更がなくなった下書きは削除する。成功応答を受けても、その送信時から編集番号が変わった入力は消さない。適用済み値はバックエンドの応答を使う。

「設定を適用」はmanualの変更だけを送り、その変更がある場合に有効にする。「元に戻す」は未適用入力と送信待ちの破棄であり、すでに実機へ適用した値を以前の値に戻さない。送信済みの要求自体は取り消せない。即時反映が止まった入力は「即時項目を再適用」で明示的に送る。

画面は項目の「即時」「ボタン」と、適用済み・未反映・送信待ち・適用中を表示する。エラーと他パネルの更新通知は必要な場合だけ表示する。

## 送信制御

- 通常は150ms間隔を初期値とする。最初の変更からタイマーを動かし、入力のたびに待ち直さない。操作中も継続送信し、待機中は各項目の最新値へまとめる。
- 同じ機器へは全パネルを通じて1件ずつ送る。別機器はそれぞれ処理できる。既存の並行更新禁止を迂回せず、送信時にoperationPolicyとlocked_settingsを確認する。
- 数値欄の空欄・入力途中の不正値は送らない。ポインター操作終了、Enter・矢印キーの操作終了、フォーカス移動で最終値を確定し、進行中の送信後に待機分を処理する。
- 即時反映はimmediateだけ、ボタン適用はmanualだけを、送信直前の最新設定へ重ねる。APIが設定一式を受け取る契約を維持し、未編集項目・ROIを古い値で上書きしない。同値ならHTTPを省略する。
- 即時反映の通信中も数値を編集できる。切断・取得・記録開始停止などとの競合制限は共有ストアの方針を使う。
- 失敗・結果不明は入力を保持して待機分を停止する。再取得・再接続・再表示だけでは再送せず、状態確認後の明示的な再適用を必要とする。
- 対象変更、ビューの非表示・破棄、切断、起動ID変更では待機分を取り消す。下書きの保持とは分ける。送信済みの応答は元のパネル・機器・セッションへ結び付け、新しいセッションの入力へ適用しない。

150msは実機の応答性能を保証しない。遅い応答では送信完了まで次を待ち、操作中の値を集約する。記録中は設定通知・履歴の負荷を実測し、必要になった段階で調整する。

## デバイス追加手順

1. `devices/<機器種類>/settings.ts` に設定型・編集値・parse・getInputs・merge・modesを置く。適用方法は編集キーすべてを型で確認する。入力範囲や選択肢は機器仕様に基づける。
2. 同じフォルダに専用フォームを作る。`SettingsFormProps`に機器の設定型・編集値型を指定し、共通画面への通知だけを行う。
3. `settingsContracts.ts` に `DeviceInfo.type` と設定処理を1件登録する。共通設定型は登録から導出するため、別の型一覧へ重ねて追加しない。
4. `settingsForms.tsx` に同じキーでフォームを登録する。登録漏れ・余分なキー・型の異なる組合せをビルドで確認する。
5. 設定応答・入力変換・最新値への差分結合・適用方法と、機器固有の表示を確認する。Workspace、Panel、既存フォーム、共有ストアへの種類別分岐追加は不要。

同じ種類で設定仕様が同じならフォームを共有する。将来、表示だけが異なる機種が必要になった場合はその種類のフォルダ内に小さな表示定義か専用フォームを追加する。現時点では機種プロファイル機構や新しい識別子を追加しない。既存のAPIやデータ形式で表現できない機能には、別途共通API・受信処理の変更が必要になる場合がある。

## 確認範囲

`npm test`、`npm run build`、`npm run lint`と、`frontend/tests/workspace/run.py --suite devices`で既存のデバイスUIを検証する。応答検証、未登録種類、単位変換、差分結合とROI保持、入力保持、記録ロック、失敗・結果不明、送信の集約・直列化・取消しを対象とする。

静的確認、Nodeテスト、ブラウザ、WebView2、実バックエンドのダミー機器、実機を分けて報告する。ダミーカメラは露光時間・ゲインを保持するだけで、合成画像の明るさには反映しない。ダミーで設定値を更新できても、実機の撮影中変更や画像への反映の確認にはならない。今回、バックエンドAPI・ダミー画像生成は変更しない。

2026-11-08の移行確認：Nodeテスト83件、build・lint成功。Edgeと表示したWebView2を実バックエンドのダミー機器へ接続し、設定・ロック・入力保持・失敗停止・待機取消しを確認した。各環境で、45msごとのゲイン入力10回は3回のPUTにまとまり、保存された設定履歴は開始時を含め4件だった。700msの応答遅延中の2パネル操作は3回のPUTへ集約し、同一機器の最大並行件数は1件。実機の撮影中変更・画像への反映、長時間の記録負荷は未確認。
